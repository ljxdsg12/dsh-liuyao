## 三、核对时额外发现的问题（动手前请先看）

核对你仓库的**远端真实状态**时，发现三处不一致，都会影响提交后的用户体验：

| 发现 | 证据 | 影响 |
|---|---|---|
| **v0.2.0 没有建 Release** | GitHub 上只有 1 个 Release：`v0.1.0`（2026-10-10 发布，资产 `dsh-liuyao-0.1.0.tgz`） | 任何人想按 `releases/download/v0.2.0/...` 下载都会 404 |
| **远端 `v0.2.0` 标签停在旧提交** | 远端 tag `v0.2.0` → `fb7eab7`；本地 tag `v0.2.0` → `dfbd0f9`（= 本地 HEAD）。差 2 个未推送的提交 | 标签指向的代码不是最新的那一份 |
| **2 个提交没推上去** | `origin/main` = `fb7eab7`，本地 HEAD = `dfbd0f9` | 远端缺「追问改为全 AI 判定」这次改动 |

另外：远端 `main` 的 `package.json` 里版本号已经是 `0.2.0`、`dsh.bundle` 也在——
**所以 CI 的 `dsh.bundle` 和仓库年龄两项都不受影响**，上面三处只关系到「用户拿到的是哪一版代码」。

**建议顺序**（代理 7897 现在通，实测 `github.com` 与 `api.github.com` 都返回 200）：

1. 推送那 2 个提交
2. 把本地 `v0.2.0` 标签强制推到远端（让标签与代码对齐）
3. 用当前代码重新打包 `dsh-liuyao-0.2.0.tgz`（本地那个是 10-10 打的，不含新的 `screenshots.json`），作为资产挂到 v0.2.0 Release
4. 再走下面的收录提交

这 4 步做完，`tarball:` 字段才有意义（见第四节）。**若你只想先收录、暂不发版，可以跳过 1–3，
但那样条目里就不要写 `tarball` 字段**，保持源码安装即可。

## 四、正式提交：两种路径，选一个

官方规则：**不要直接改两个 README**（它们由 `data/plugins/*.yml` 自动生成）。
一个 PR 只新增**一个文件**：`data/plugins/<owner>__<repo>.yml`。

你这个文件的内容就是（**这是全部提交内容**）：

```yaml
url: https://github.com/LJXDSG12/dsh-liuyao
name: LJXDSG12/dsh-liuyao
category: fun
description:
  en: Six-yao (I Ching) divination for DeepSeek Harness — xiantian bagua backdrop, ...
  zh: DeepSeek Harness 的六爻算卦插件——先天八卦盘背景、周易开场辞、 ...
```

> 文件名必须严格是 `LJXDSG12__dsh-liuyao.yml`（`__` 是两个下划线，owner 大小写跟 GitHub 显示一致）。

### 路径 A：网页操作（推荐，零门槛，约 5 分钟）

1. 打开 <https://github.com/awesome-dsh-plugin/awesome-dsh-plugin>
2. 右上角 **Fork** → Create fork（fork 到你自己的账号下）
3. 在 fork 出来的仓库里点进 `data/plugins/` 目录 → **Add file → Create new file**
4. 文件名填 `LJXDSG12__dsh-liuyao.yml`（注意别被自动补成 `.yml.yml`）
5. 内容粘贴本仓库 `submit/data/plugins/LJXDSG12__dsh-liuyao.yml` 的全部内容
6. 页面底部 **Commit changes** → 选 **Create a new branch for this commit and start a pull request**
7. 回到主仓库，点 **Compare & pull request** → 填标题（如 `Add LJXDSG12/dsh-liuyao`）→ **Create pull request**

### 路径 B：命令行（本工作区代做，需你提供 GitHub 授权）

本机目前**没有任何 GitHub 凭据**（无 `GH_TOKEN`、无 `.git-credentials`、无 `gh` CLI），所以我无法直接替你推送或建 PR。若要自动化，二选一：

- **给一个 token**（Fine-grained PAT，权限只需 `public_repo` + `read:user`）：我用它 fork、建分支、提交、开 PR，用完请你立即到 GitHub 撤销该 token。
- **装 gh CLI** 走设备码登录：你在浏览器里输一次 8 位配对码，之后全程免 token。

## 五、可选增强（不做也能过）

### 1. 声明 `tarball` 字段 —— 建议做

官方明说：仓库无法从源码安装时，`tarball` 字段是**必需**的。你的仓库**恰好属于这种**——
你自己实测过公网 tarball 直链安装会报 `ERR_PNPM_MISSING_TARBALL_INTEGRITY`（见 `KNOWN-ISSUE-install.md`）。
有了这个字段，市场会**优先展示 tarball 安装**而不是源码构建，对用户更稳：

```yaml
tarball: https://github.com/LJXDSG12/dsh-liuyao/releases/download/v0.2.0/dsh-liuyao-0.2.0.tgz
```

官方对 `latest/download/` 有明确警告：**它只解析 `latest`，文件名按字面取**，
资产名里带版本号就会「提交当天有效、发下一版就 404」。所以这里用**钉住 tag** 的写法（如上），
带版本号的文件名在这种写法下反而是官方认可的正常做法。

**前提**：v0.2.0 的 Release 必须先建出来、资产名必须是 `dsh-liuyao-0.2.0.tgz`。
**目前这个 URL 实测返回 404**（因为 v0.2.0 根本没建 Release，见第三节）。
所以：**先补完第三节那 4 步，再把 `tarball` 这一行加进条目文件**；顺序反过来会直接指向一个坏链接。
（校验脚本 `scripts/check-market-entry.mjs` 允许出现 `tarball:` 键，但加之前请先确认那个 URL 返回 200。）

### 2. 发布到 npm —— 可选

好处是市场能显示下载量，且预构建安装可跳过 `allowBuilds` 构建授权。
收录与否不受影响。注意官方要求：npm 包里的 `repository` 字段必须指回本仓库（你已满足）。

### 3. 分类选择

我填的是 `fun`（官方分类表里的合法值之一，README 里的显示名可能是「Fun & Misc / 趣味与其他」）。
官方对分类的原话是：**没人会因为分类被打回**，选得不够贴切维护者会直接改。
你这插件是娱乐/文化向工具，`fun` 是最贴切的；若维护者认为该并入 `usage`，他们会自己动手。

## 六、描述文字的两条官方红线（我写条目时已避开）

官方原话，抄在这里给你提个醒：

> **描述必须属实。** 它会被当作对你插件的声明，并与代码核对。
> 写「46 个工具、六大领域」，就应该真有 46 个工具和六个领域；提到某个命令或 API，它就应该存在。
> **夸大是让一个本来不错的插件被打回的主要原因。**

> 描述只说功能，**不带营销词**。

所以条目里我写的是「逐条注明典籍出处」「零 npm 依赖」「除模型调用外不访问网络」这类**可被代码验证**的陈述，
没有写「最准」「业界首创」这类话。**你也别让我往里加。**

另外官方特意说明：**因描述不准确被打回不是对插件的否定**，改好那一行就能收录；
CI 失败也在同一分支推修复即可，不用重开 PR。

## 七、两个官方特意写长了的坑（你这插件都躲过了，记下来备用）

### 1. `dsh.client` 不等于可安装（最常见的被拒原因）

官方原话：**大多数被拒的投稿只声明了 `dsh.client`——那样无法安装。**
必须声明的是 `dsh.bundle`：

```jsonc
{
  "dsh": {
    "bundle": { "patch": "./cordis.patch.yml" },  // ← 必须
    "client": { "platform": "web" }               // 仅带前端 UI 时才需要
  }
}
```

你的 `package.json` 里 `dsh.bundle` 和 `dsh.client` 都有，`cordis.patch.yml` 也在仓库根，
**这条不会卡你**。以后写别的插件时注意别只写 `client`。

### 2. `peerDependencies` 的范围会静默排除预发布版 harness

这条只在你以后引用官方 `@deepseek-ai/*` 包时才相关（你现在零依赖）。

官方说明：node-semver 只有当范围里**某个比较符与该版本的 `major.minor.patch` 元组完全一致、
且自身也带预发布标签**时，才放行预发布版本。所以看起来「匹配一切」的范围其实匹配不到
`0.1.0-rc.6`，用户会撞上 `ERESOLVE`：

```jsonc
// ❌ 看着很宽，却静默排除所有 0.1.0-* 预发布版
"peerDependencies": { "@deepseek-ai/dsh-tools": ">=0.0.1-rc.1 <0.2.0" }

// ✅ 在 0.1.0 元组上显式加预发布分支
"peerDependencies": { "@deepseek-ai/dsh-tools": ">=0.0.1-rc.1 <0.1.0 || >=0.1.0-rc.1 <0.2.0-0" }
```

本机 DSH 是 `0.2.0-rc.2`，正好属于容易被静默排除的预发布版本。
